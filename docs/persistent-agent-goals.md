# Persistent Agent goals

A goal keeps an objective and completion contract attached to one chat across bounded Agent runs. Typing `/goal` offers a goal composer; `/goal start <objective>` also starts directly. `/goal status`, `/goal pause`, `/goal resume`, `/goal stop`, and `/goal clear` inspect or control the saved goal. Clear removes its visible controls. A normal composer message pauses active automatic goal work before it is queued. When a goal is blocked or needs user input, an Agent-mode reply continues the saved goal with that reply and its original execution settings. Manually paused goals stay paused until Resume. Replies do not grant permissions or replace pending tool-approval controls. A status change detected before sending preserves the reply draft; the server also rejects a resume if the goal was paused or replaced after that check.

The completion contract has one to eight success criteria and optional verification command, constraints to preserve, scope boundaries, and conditions requiring user input. Multiline commands accept `criterion:`, `verify:`, `preserve:`, `scope:`, and `stop when:` fields. The goal bar sits above the composer. Editing opens the Computer sidebar on desktop and its full-screen overlay on mobile, with a single goal text editor. Saving preserves elapsed work time and clears evidence for the old objective. A goal saved while running or queued continues automatically with the revised objective; a paused, completed, waiting, or approval-pending goal stays paused until explicit Resume.

Editing and resending the latest goal message starts a fresh attempt: the message and saved objective change atomically, elapsed time and progress reset, and the previous completion receipt is removed with the regenerated response. The saved sandbox, model, permissions, and explicit completion requirements are preserved. If admission fails, the revised goal remains paused for Resume. This differs from refining a goal through the sidebar, which preserves accumulated work time.

Goal messages retain a sent-as-goal receipt. Verified completion saves cumulative active goal time on the final assistant message. Pauses and waiting are excluded; resuming continues from the saved duration. These receipts survive reload, goal deletion, and replacement; ordinary completed runs receive no achievement receipt. Older goals without a recorded start time do not receive an invented duration.

## Limits and completion

Goals have no fixed run-count limit or Goal-specific time slice. Each run uses the ordinary Agent plan runtime and remains subject to the existing step, context, spend, approval, cancellation, and sandbox limits. When an Agent run stops without verified completion or reaches an ordinary step, context, or runtime limit, the goal checks whether work should continue. Automatic continuations use fresh workers and preserve saved progress. Normal usage exhaustion leaves the goal unfinished and requires explicit resume after usage becomes available. Legacy goals stopped at the old run cap remain paused until the user resumes them; no run extension is needed.

Completion of external work requires saved assistant tool results for every criterion and a separate bounded model check. An optional verification command must finish successfully through the existing terminal and approval path in the final run. A goal whose entire deliverable is text in chat can instead complete from its final response: the evaluator checks the full text against every requirement, and a separate classification of the user goal alone must confirm that no external work is required. Settlement revalidates the exact evaluated text against the saved final assistant message. This path rejects truncated responses, turns with tool calls, and explicit verification commands; it cannot turn an unverified claim about external work into completion.

After a normally finished Agent turn, the harness automatically evaluates its final response, executed tool results, and previously saved evidence. The Agent does not call a checkpoint tool or need to claim completion first. The evaluator can continue useful work, wait for missing user input or an authorized delay, block for intervention, or verify completion. A question can require user input even when no tool has run. Evaluation costs, including the additional classification when needed, are billed through the run's normal usage settlement; verification failure blocks automatic work for review. User cancellation, failures, and usage exhaustion take precedence over any evaluation. Ordinary Agent runs do not use this evaluator.

The legacy checkpoint mutation and stored checkpoint fields remain compatible with already deployed workers. New workers save the automatic decision and validated evidence together when settling the run. Intermediate tool-call steps do not trigger goal evaluation; a final `tool-calls` finish is eligible only at whole-turn settlement, while normal `stop` is the usual final-response case.

Goals can wait up to thirty minutes before another run. Two consecutive runs without usable tool results stop for review. These checks bound automatic work; they are not guarantees that every tool result represents useful progress or that model judgment is infallible. The chat retains the evidence for user review.

## Durable lifecycle

Convex owns the goal, generation, work count, progress, and evidence references. Trigger runs claim one generation atomically before performing costly work. Stale or duplicate workers cannot claim it. Pause, edit, and delete remain authoritative when a late worker settles. Deleted goals retain an internal tombstone until replacement so stale generations cannot claim work and interrupted run leases can still reconcile. Goal state survives context compaction because each new run reads the canonical record alongside the existing chat history.

A short dispatcher starts the next normal Agent run only after the preceding run has settled and cleaned up. Continuations retain the original sandbox, model, permission mode, region, Convex URL, and worker version. Approval modes open the existing approval session protocol. Fresh account, suspension, and feature eligibility checks run before each new run. Failed runs and usage exhaustion require explicit resume.

If a worker terminates before saving its final state, loading goal status reconciles the recorded run against Trigger after checking its chat and user metadata. Reconciliation never infers success from a completed Trigger status. A queued goal whose dispatch could not be reconciled can be paused and explicitly resumed to fence the old generation.

## Rollout and verification

Persistent goals are available to paid Agent users without a rollout flag. New runs and continuations recheck the current subscription, organization, and suspension state; ordinary usage and billing limits still apply. Existing saved goals retain their pause, edit, and delete controls even when execution access changes. Goal analytics are independent of eligibility and contain identifiers, categorical states, and counts; they exclude objectives, criteria, prompts, commands, and evidence.

`agent_goal_lifecycle` records admission, resume, worker claim, settlement, recovery, user controls, and continuation scheduling/start/failure. `goal_attempt_id` separates replacements of the same goal record; `goal_generation` fences continuations, and `trigger_run_id` joins existing Agent diagnostics. Retried emissions share a deterministic event UUID. Use `snapshot_updated_at` to order persisted state snapshots rather than ingestion time; dispatch observations can arrive after a newer worker snapshot. Cleared goals have `deleted: true`. Failures without a snapshot do not assert a persisted state. `elapsed_ms` uses the same cumulative timer as the UI. Count unique attempts, not settlement events, for outcomes; paused, waiting, input-required, and budget-exhausted states are not infrastructure failures. Telemetry is best effort and cannot fail execution. Missing events alone do not prove a stalled worker; confirm its recorded Trigger run and canonical goal state.

Deploy the Convex functions and Trigger worker before testing goal admission in the web Preview. Independently verify the Vercel, Trigger, Convex, and PostHog selections according to `AGENTS.md`. Preview uses the Developer account and development PostHog project; Production requires a separate rollout decision. A feature-flag definition alone does not prove that the worker uses the expected project.

Acceptance should exercise a real two-run goal, persisted progress after reload, independent completion, a failed verification command, Pause during work, Stop between runs, approval waiting, continuation past the former run limits, no-progress stopping, and safe recovery after a canceled or failed worker. Test a connected local or Desktop sandbox separately from cloud because those transports have different availability and reconnection behavior.

The composer Stop button pauses the saved goal before canceling its active run. Resume stays visible but disabled during cancellation cleanup, then continues from saved progress. Canceled runs also settle as paused if cleanup wins the race; explicit `/goal stop` and `/goal clear` retain their stopped/deleted semantics.
